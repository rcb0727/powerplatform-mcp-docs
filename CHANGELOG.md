## [0.17.0] - 2026-09-07

- **Trimmed the eight heaviest Copilot Studio tool descriptions to cut the tools/list token cost, with no change to any tool's behavior or input schema.** Removed provenance dates, internal-mechanism notes, exhaustive never-projects enumerations and repeated hedges from `get_copilot_agent_activity`, `add_copilot_agent_evaluation_test_set`, `add_copilot_agent_tool`, `create_copilot_knowledge_text_file`, `get_copilot_agent_evaluation_connections`, `get_copilot_agent_session_summary`, `create_copilot_mcp_connector` and `add_copilot_agent_test_case`, while keeping every decision-relevant constraint (read-only/own-user scope, required companion arguments, destructive/cascade and confirmation warnings, evidence-is-not-proof). Every test-pinned safety phrase is preserved verbatim. Saves ~700 tokens (-1.3%) off the primary's ~55.6k tools/list payload. Suite 7003 passed; typecheck, lint, docs:check and build green.

- **Recorded getJiraIssue evidence gains a `comment-only` read contract, and one live run exercised it.** `get_copilot_agent_activity` `toolResultTarget.fieldSelection` now also accepts `comment-only`, which requires the recorded call to have bound `fields:[comment]` and projects at most the last three RETURNED comments in service order — id, created/updated instants, bounded redacted body, visibility presence, and the service's page counters — never authors, avatars, self links, rendered bodies or properties. Missing/denied/malformed never become zero, a projected tail is not claimed to be the newest comment overall, and an unrecognized envelope is withheld with structure-only disclosure (key names, JSON types and lengths, tagged by the container inspected) rather than a value. No new tool, route, request body, redactor or auth path; 17 sabotage-verified regressions. **Live 2026-09-07: the projection is correct and safe on a real recorded envelope, but no actual PROJ-123 comment was verified** — the recorded result reduced to an empty selected-fields object, so this is a passing guardrail, not an acceptance pass.

- **Opt-in evaluation-start diagnostics now also cover exact HTTP500.** `includeErrorDiagnostics=true` on `start_copilot_agent_evaluation` applies the same bounded, best-effort-redacted, untrusted server-text inspection to an exact HTTP500 as it already did to HTTP422; the prefix names the status it inspected. No parser, redaction, authentication, route, request body or retry behavior changed, and other 5xx and 401/403/429 stay on their existing metadata-only paths. Live, the first inspected500 (correlation `a correlation id`) carried a JSON object with no supported message field — an observation, not a diagnosis.

- **The token allowlist's acceptance of per-tenant Dataverse hosts is now pinned by test.** A Dataverse audience is the tenant's own organization host (`contoso.crm4.dynamics.com`), so it can never appear in a static resource list; this package's providers already admitted it through the shared domain allowlist and were unaffected, but nothing asserted it, and the Azure CLI sibling shipped an exact-match gate that refused every tenant ([rcb0727/powerplatform-mcp-server#1](https://github.com/rcb0727/powerplatform-mcp-server/issues/1)). The invariant now has explicit coverage against the real WAM provider rather than the stubbed auth every other Dataverse test uses, and both packages share one `isDataverseTokenResource` helper so the rule is stated the same way in each.

- **Knowledge partial failures and file validation remain explicit.** Recognized partial storage outcomes now return MCP `isError: true` while preserving the possible new component/orphan ID and per-stage evidence, without a retry or rollback claim. Uploaded type-14 file components are explicitly excluded from YAML validation instead of producing a false empty-source error; they remain unvalidated, not ingestion-ready. The 28-test knowledge dispatch suite and 21 file-validator regressions cover these distinctions.

- **Typed tool replacement is source-guarded across action kinds.** Existing flow, connected-agent, connector and MCP replacements require an inspected full-source hash, unique complete lookup and exact current identity/schema/action-kind checks before one conditional PATCH. Stale or incompatible rows cannot fall back to an unguarded update or create. Explicit custom MCP input/output arrays, including empty arrays, are refused before I/O rather than silently ignored; arbitrary per-tool default/schema authoring is not claimed. Offline regressions and a primary live no-write kind-collision check cover the safeguards.

- **Recorded exact-target tool results are available through MCP.** Optional `includeToolResults` on `get_copilot_agent_activity` requires a reviewed exact target and owned history, then returns only supported minimal `getJiraIssue` evidence after matching recorded binding, arguments, result identity and non-error state. Default metadata-only output is unchanged; values are bounded and conservatively redacted. The primary read the historical successful PROJ-123 result through normal MCP, not a new execution or current-state Jira read.

- **Experimental knowledge text-file storage and Monitor metadata.** New `create_copilot_knowledge_text_file` previews a hash-pinned inline plan, creates only a new exact-agent file component, uploads once and independently verifies metadata and bytes; partial/orphan outcomes are explicit and ingestion remains unknown. New `get_copilot_agent_session_summary` exposes bounded non-exhaustive Monitor metadata without transcripts. Primary live checks verified a synthetic 160-byte file and 23 Monitor rows. Native Knowledge still showed General / Status Unknown; Teams was not added and the existing publication was unchanged.

- **Eight-item Rovo acceptance evidence remains explicit about unfinished work.** The private validation report separates implemented safeguards, offline tests, live observations and blockers. Its 14-scenario HELP/HR matrix is unexecuted, not an enforcement layer or authorization to mutate tickets. HR needs an exact target; writes require a fresh exact preview, per-write user confirmation and independent before/after evidence. No Jira mutation, publication or permission change occurred in this continuation.

- **Evaluation rejection diagnostics identify what was safely inspected.** Primary formal-evaluation HTTP errors now preserve closed body-read, code-field and MIME-family states through ordinary MCP dispatch, without exposing arbitrary bodies or inventing a rejection cause. One live controlled start returned HTTP 422, a JSON object with absent inspected code fields, and no run ID; the cause remains unknown and the separate binding 403 is not treated as its explanation. No POST retry or sibling formal-evaluation family was added.

- **Typed topic replacement cannot silently overwrite an MCP tool.** Existing `add_copilot_agent_topic` replacements now require an inspected full-source hash, a unique complete lookup, exact AdaptiveDialog identity and a fresh row ETag. One conditional source update preserves stale-write failures and reports independent readback; TaskDialog collisions and guarded creation are refused. Forty-five new offline regressions cover the guard. Ordinary topic creation remains unchanged.

- **Activity can return explicitly requested, bounded bot messages.** `get_copilot_agent_activity` adds `includeBotMessages=true` after the existing exact-user/agent/evaluation ownership checks. Default output stays metadata-only. Five-message, per-message and total-text limits include omission counters and conservative credential/URI redaction; ordinary Markdown labels are retained. Text is sensitive, untrusted and not execution proof. The primary's rebuilt MCP read the recorded PROJ-123 answer after a successful narrow evaluation; sibling live authentication parity remains unverified. ## [0.8.0] - 2026-05-06

### Added
- **`get_flow` `format` parameter (`"summary" | "json" | "both"`)**: The previous output rendered only top-level actions and silently dropped everything nested inside `Switch`/`If`/`Foreach`/`Scope` controls. Round-tripping a flow with nested branches through `get_flow` → `update_flow` lost the nested actions. The new `format="json"` mode returns the raw `flow.properties.definition` JSON with every nested action preserved; `format="both"` appends the JSON after the human-readable summary. The `summary` default is unchanged for back-compat. The summary output also now surfaces flow `description` and creator (owner). Use `format="json"` whenever you intend to call `update_flow` on a flow with nested controls.
- **`update_flow` `mergeActions` mode**: Set `mergeActions: true` to deep-merge the actions you provide onto the current flow definition instead of replacing wholesale. Recurses into `actions`/`cases`/`else`/`foreach` so siblings you didn't pass are preserved. Solves the wholesale-replace footgun where omitting any action caused it to be deleted.
- **`update_flow` `patchActions` (path-based, smallest payload)**: Pass a map of slash-separated paths to action values, e.g. `{"If_Recognized_Form/cases/Default/actions/Compose": {...}}`. Each entry surgically replaces (or, when value is `null`, deletes) one node in the action tree. Ideal when an LLM client has per-tool-input size pressure — a surgical edit is typically a fraction of the full action tree (~31% of the full payload in our smoke tests for a representative Switch with cases). `patchActions` is applied AFTER `mergeActions` so they compose.
- **`description` on `create_flow` and `update_flow`**: Optional `description` parameter sets the flow description shown in the Power Automate UI. On `update_flow`, an empty string clears the description; `undefined` leaves it unchanged. The field is also surfaced by `get_flow` in both summary and JSON output.
- **`list_flows` ownership filter**: New `scope` parameter (`"owned" | "shared" | "all"` — default `"all"`) filters results client-side by comparing `flow.properties.creator.id` against the current user's Azure AD object ID (extracted from the access token). Use `scope="shared"` to surface flows that have been shared with you that you didn't create. The new `includeOwner` flag (default `true`) tags each row with the owner display name plus an `[owned]` / `[shared]` indicator.

### Changed
- **`FlowProperties` and `CreateFlowRequest` types now include optional `description: string`** to match the Power Automate Flow Service API surface. Internal helper `getCurrentUserOid()` was added to `FlowManagementApi` to expose the current user's object ID for ownership filtering, derived from the existing access token (no extra Graph calls).

### Upgrade Notes
- `npm install -g powerautomate-mcp@latest`. No app-registration, configuration, or workflow changes required.
- All v0.8.0 additions are additive and backwards-compatible. Existing `get_flow` / `update_flow` / `create_flow` / `list_flows` calls continue to work exactly as before.
- Recommended workflow when editing a flow with nested controls: call `get_flow` with `format="json"` to capture the full definition, then call `update_flow` with either `mergeActions: true` (delta-only) or `patchActions` (surgical) to avoid resending the entire action tree.
